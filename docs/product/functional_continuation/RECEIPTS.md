# Continuation evidence and receipt contract

This document specifies how a later coordinator-owned verifier may certify the bounded continuation. It is **not an execution receipt**. The current103-candidate plan alone certifies zero additional points. Historical checkpoints are exact-source observations and cannot certify a later tree; the ac8f517 checkpoint also records the post-run native audio visibility finding. No historical matrix, acceptance result or previous scope plan is rewritten.

## Source and scope integrity

Before recording any point as completed, the verifier must:

1. Read the 556-row original inventory at the exact path and SHA-256 in `scope_plan.json.source_inventory`; verify 556 unique original IDs.
2. Compare every included point's exact original text and direct specification IDs with that inventory. Verify the separately pinned specification/decision source digests.
3. Read the unchanged prior 57-point scope plan and compare its digest and exact IDs with `previous_batch`. Reject duplicate current IDs and any overlap with those prior credited IDs or the current exclusions.
4. Require actual implementation and final evidence for all103 candidates. A plan, enum, UI placeholder or reported local pass cannot mark a candidate complete. The scope revision adding point361 records the actual video export/reimport proof that justified its promotion; the final run must execute that scenario too.
5. Compute the percentage from the actual newly completed IDs divided by 556. Do not use the 479 detailed clauses, tests, commits, files, messages or elapsed work as that denominator.

The historical intermediate target is56–66 original points for an additional10–12%; the current user goal is the remaining documented functionality except final visual design. Neither target is an achieved result by itself. A receipt must report only its actually verified whole-point count and exact percentage. An intermediate milestone does not establish overall product completion.

## Exact tested tree and run

A full receipt identifies the actual tested commit, clean tracked tree, source-plan digest, Python/Django/PostgreSQL versions, test labels, every stage's command, exit status and log digest. Test output must be from the same integrated commit; a service run before later permission or route edits is not an exact final-commit result.

The existing protected verification principles apply:

- Use only a freshly created, invocation-owned synthetic PostgreSQL database and the established ownership guards. A cleanup failure is a failed run, not a passing receipt.
- Execute both supported PostgreSQL majors. Do not substitute SQLite or suppress database triggers.
- Check registered migrations and configuration, affected existing regressions, all selected new service/native labels and the actual offline Node tests.
- Run all selected native workflows through `config.campaign_urls`; an isolated app route wrapper is insufficient as the only integration proof.
- Preserve existing feature flags, source contracts and default-deny policies. Missing source bytes, provider snapshot support or explicit authority must fail closed.

The coordinator may write fresh aggregate receipts under `.local/qa/functional-continuation/pg17/` and `pg18/`. If it chooses another directory, that exact path must be recorded rather than guessed or discovered from stale artifacts.

## Protected browser requirements

The current registry requires51 exact executed browser identities (8 inherited plus43 continuation),50 native JSON proofs and1 original audio execution-log proof. An unrelated replacement identity cannot satisfy the aggregate. For every claimed functional group, execute the test class and read the exact result path listed in the scope plan. Where a class/module is marked planned, first require its actual implementation and registration. A name in this document is not proof that the test exists.

Each successful result must attest `status=PASS`, sandbox enabled and widths 320 and 1280, with fresh screenshots and trace files. The aggregate verifier should retain their byte hashes and the test invocation/log that produced them. It must check actual freshness within this run, not merely the existence of a JSON file carrying PASS.

The scenarios must use actual native forms and separate authenticated actors where independent approval is required. They must exercise meaningful anonymous or requester output, permission/withdrawal behavior and the correct canonical target after a write. Protected execution may not use sandbox-disabling flags, monkeypatch successful responses, replace failed commands with fake receipts or bypass CSRF/authentication.

For offline work, a server response alone is not sufficient. The browser must register the service worker, save an explicitly selected material under current OFFLINE authority, change to an offline network state, read the actual saved material, and verify expiry/online reconciliation and explicit removal. Automatic caching is restricted to the static application shell. Actual download/archive contents must be inspected, including file bytes, references and manifest pins.

A local environment that cannot launch protected Chromium records `PENDING_PROTECTED_BROWSER` or `NOT_RUN`, with zero completed-point credit for that incomplete aggregate run. It is not a reason to weaken browser isolation.

## Recovery requirements

The integrated encrypted recovery drill must populate and restore every persistent table used by the included groups' explicit inventory. That inventory covers93 nonempty tables:22 inherited and71 continuation-covered tables. The continuation inventory consists of4 library,7 import,3 collection,1 lifecycle,2 canonical search,4 public recording/transcript,3 precise citation,1 existing original-attachment,3 existing answer-media,6 identity,2 scheduling,3 destination-publication,7 development-taxonomy,4 synonym/shadow-governance,3 public-teaching,1 retry 4 evaluation/benchmark,1 priority-history 3 AI audit/derivative tables and4 session/proof journals plus1 classification journal,1 permission journal and3 upload quarantine/scan journals. Existing tables are additionally covered, not counted as newly created schema. Recording search reuses search/media owners. Offline reading, staff PWA, dark mode, the separate composer panel, public reader actions, the material API, text-only selection, FT lookup and the operational queue add no server tables. The38 exact fresh-process helper records and266 actual current-access denial reads must match their explicit registries, with positive reads after authority restoration.

The drill must verify:

- Every expected table is nonempty; complete row/sequence inventory is captured and restored.
- Every actual stored source file and external storage reference remains present with the same bytes and identity.
- Immutable trigger/functions and foreign-key protections survive restoration and continue rejecting mutation/deletion.
- The original frozen source database remains unchanged by backup, restore and the fresh-process readers.
- Fresh readers can reopen exact canonical library/import results, a reviewed/released collection and a closed/archived lifecycle record under new explicit fixture authorities within the original deadlines.
- Removing the configured identity/authority denies those reads. A stored review/release event never creates a new access grant.

The helper contract is `populate()` plus `verify_restored(pins)` in each app's `recovery_support`. Source hashes, exact row/version IDs and deadlines are data pins, not credentials. The coordinator owns any shared inventory/schema integration. App-local helper tests are not themselves encrypted restoration evidence.

`PASS` requires all mandatory stages and their final-state checks. A failed, missing, skipped, stale or unexecuted required proof keeps the affected result pending/failed; it cannot be converted into completion by editing documentation. If a group is removed from the batch, update the exact scope before the run and record the reduced result. The original requirement remains in the unchanged inventory.

A verified development functional receipt does not alter Gate B, Gates C/D/E, Phase01, production deployment or acceptance of pending detailed policies. Those are separate decisions.

The upload candidate additionally requires the actual ClamAV prerequisite artifact from the same workflow run and exact commit, with official signed databases, complete benign CLEAN and EICAR BLOCKED observations, and retained process reports. Synthetic scan-control tests cannot satisfy this requirement. A failed prerequisite still allows collection of the other diagnostic stages, but the final receipt rejects absent or failed real-engine proof. No production scanner or role policy is enabled.
