# FAST9 — Multipart Delivery Ledger v1 + Provider Receipt Journal

التاريخ: 15 نوفمبر 2026.

**الحالة: تطوير محلي اصطناعي، NOT_DEPLOYED / GATES_HOLD.**

## الوظائف
- تجميع جميع أجزاء خطة واحدة وفق بصمة الخطة الدقيقة.
- لا تصبح الخطة DELIVERED إلا إذا كانت جميع الأجزاء DELIVERED.
- PARTIALLY_DELIVERED عند وصول بعض الأجزاء فقط، وPARTIALLY_FAILED عند اجتماع النجاح والفشل، وNEEDS_RECONCILIATION عند وجود جزء غير محسوم.
- إضافة جدول append-only باسم provider_receipts في Outbox schema v3.
- جعل receipt_reference فريدًا على مستوى المخزن كله، مع بصمة payload تربط المرجع بالقضية/الجزء/معرف رسالة المزوّد/الحالة.
- إعادة الإيصال نفسه حرفيًا عملية idempotent؛ إعادة استعمال المرجع مع payload مختلف أو intent آخر تُرفض.
- حفظ سجل الإيصال وتحديث حالة الجزء وإضافة حدث التدقيق داخل معاملة SQLite واحدة.
- التحقق من اتساق كل إيصال مع intent وحدث التدقيق عند كل قراءة.
- لا ترسل هذه الوظائف شيئًا ولا تتصل بمزوّد قناة؛ تعتمد على verifier خارجي يقدمه المستدعي.

## اختبارات
تغطي الاختبارات: التسليم الجزئي والكامل، الفشل الجزئي، انتهاء الحجز، الإيصال المكرر المطابق، إعادة استخدام receipt_reference مع محتوى مختلف، وحماية السجل من التعديل.

## حدود
الذرية محلية داخل ملف SQLite واحد. لا يوجد مزوّد حي أو sender أو distributed transaction. ملفات schema v1/v2 تُرفض fail-closed ولا تُرقّى تلقائيًا؛ يلزم مسار ترحيل مستقل قبل أي بيانات محفوظة غير اصطناعية.
