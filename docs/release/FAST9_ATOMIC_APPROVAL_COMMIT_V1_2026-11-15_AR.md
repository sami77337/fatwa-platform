# FAST9 — Atomic Approval & Delivery Commit v1

تاريخ الدفعة: 15 نوفمبر 2026.

**الحالة: تنفيذ تطويري محلي ببيانات اصطناعية، NOT_DEPLOYED / GATES_HOLD.**

## الهدف

سد فجوة إعادة استخدام إيصال اعتماد المفتي لخطة تسليم أخرى، وضمان أن حجز الإذن المحلي وخطة التسليم المقصودة يُحفظان كوحدة SQLite ذرية واحدة.

## التغييرات

- ترقية مخطط Outbox الاصطناعي من schema version 1 إلى version 2.
- إضافة جدول `approval_claims` بمفتاح أساسي فريد على `receipt_id`.
- ربط الإيصال ببصمة الاعتماد وبصمة الخطة والقضية والنسخة وبصمة المصدر والرد وهوية المفتي وkey_id وnonce.
- إنشاء سجل الاعتماد ونوايا كل أجزاء الخطة داخل معاملة SQLite واحدة `BEGIN IMMEDIATE`؛ لا تُحفظ المطالبة إذا فشل إدراج أي جزء.
- السماح بإعادة الطلب المطابق حرفيًا كعملية idempotent، مع رفض إعادة استعمال الإيصال لخطة أو مصدر مختلف.
- حماية جدول المطالبات من UPDATE/DELETE بواسطة triggers، والتحقق من اتساق المطالبات مع intents عند كل قراءة.
- إعادة التحقق من وجود المطالبة المطابقة قبل حجز أي جزء للإرسال.
- اختبارات تزامن متعددة العمال، وخطة متنافسة على نفس الإيصال، واستمرارية بعد إعادة الفتح، والتلاعب بسجل المطالبات.

## حدود الضمان

هذه الذرية محلية داخل ملف Outbox SQLite واحد، ولا تنشئ معاملة موزعة مع مزوّد هوية خارجي أو قناة إرسال. إذا انتقلت المنصة إلى عدة أجهزة أو قواعد بيانات، يلزم سجل مركزي أو واجهة atomic claim/consume لدى مزوّد الهوية، مع idempotency key ثابت. لا يوجد إرسال فعلي أو استهلاك اعتماد خارجي في هذه الدفعة.

ملفات Outbox ذات schema v1 تُرفض fail-closed ولا تُرقّى تلقائيًا؛ لا تُحذف أو تُعدّل تلقائيًا. يلزم مسار ترحيل منفصل معتمد قبل أي استخدام لبيانات محفوظة غير اصطناعية.

## التحقق

تُضاف اختبارات المطالبات الذرية إلى FAST9 integrated journey. لا يُسجّل PASS إلا من تشغيل CI على رأس الفرع النهائي. لا تعني هذه الدفعة اعتماد سياسة U03/U10 أو فتح أي بوابة.
