# مكتب متابعة التسليم — تجربة اصطناعية مستقلة

واجهة عربية فعلية تربط خدمات #214 و#217: دخول المفتي المخوّل → فتح القضية →
معاينة خطة الإرجاع وتنزيل طلب اعتمادها → إدخال رد موقّع من جهة الاعتماد → حفظ
الخطة → متابعة كل جزء وإثباته → تأكيد معالجة الحجز المنتهي → تحديث النتيجة
عند وصول إيصال مزود موقّع متأخر. لا توليد حكم أو توقيع أو اعتماد أو إرسال من
التطبيق. اعتماد الجواب وحده لا يكفي لحفظ خطة الإرجاع.

## الملكية وعقد الدمج

كل ملفات التطبيق والقوالب والتنسيق والإعداد الاختياري داخل
`apps/case_delivery_desk/`؛ الاختبارات والمشغّل الاصطناعي داخل
`tests/case_delivery_desk/`. ملف CI جديد مستقل. لا تعديل لأي ملف قائم في
casework، واجهة السائل، واجهة الفريق، URLConf أو إعداداتها المشتركة.

الأساس هو #217 عند `a42087f7dc0ad3dd134d469a956fc1f3a6f5a6c9`، ويشمل #214.
يحتاج المنسق هاتين التبعيتين أولًا، ثم هذا الالتزام. لا سحب شامل للفروع.

الملف `apps.case_delivery_desk.settings` يختار URLConf مستقلاً بدل واجهة
casework القديمة **لهذا التشغيل المحلي فقط**. يستعمل المسارات الحالية
`/casework/staff/` و`/casework/staff/login/` و`/casework/staff/logout/` وملف CSS
المسموح به، لإعادة استخدام حارس loopback/Host/المعدل/CSRF والكوكي المقيد.
يمكن تشغيل هذا البروفايل على منفذ مستقل بجانب تجارب أصحاب الواجهات الأخرى.
لا يستبدل واجهتهم في إعداد المشروع العام. الدمج في عنوان موحد لاحقًا مسؤولية
المنسق: اختيار مسار وقائمة حارس صريحة وربط التنقل دون تجاوز الحماية أو تعارض
`/casework/staff/`؛ لا تكفي إضافة include إلى URLConf عام دون الحارس.

يتطلب البروفايل متغير `FATWA_CASE_DELIVERY_DESK_ENABLED=1`؛ الافتراضي مغلق.
إعدادات الخادم المطلوبة:

- `FATWA_CASEWORK_IDENTITY_PROVIDER`: مزود هوية المفتي القائم.
- `FATWA_CASE_DELIVERY_APPROVAL_VERIFIER`: مدقق توقيع اعتماد الإرجاع القائم.
- `FATWA_CASE_DELIVERY_PROVIDER_VERIFIER`: مدقق إثبات المزود؛ غيابه يمنع ادعاء
  التسليم المتحقق ويعرض أن التحقق غير متاح.

لا يأتي أي منها من نموذج المتصفح. تسجيل الدخول يستعمل خدمة الهوية والكوكي
المرتبطة بـCSRF وإصدار الصلاحيات القائمة، ولا يمنح أدوارًا جديدة.
كل الإجراءات POST مع أشكال حقول محددة؛ الرموز والتواقيع لا تذهب إلى URL.
الاستجابات no-store/noindex وCSP؛ لا JavaScript أو مورد خارجي مطلوب.

تنزيل الطلب لا يكتب حالة ولا يمنح موافقة. يضم `request_sha256` وبنية طلب #214.
الرد الذي يلصقه المفتي يتبع غلاف decoder القائم:
`{"request_sha256": "…", "receipt": {…SignedApprovalReceipt…}}`.
يُعاد بناء الطلب والتحقق من نسخته والتوقيع والخطة قبل الحفظ؛ الرد لا يُعاد
عرضه أو تخزينه في جلسة المتصفح. المفاتيح الخاصة ليست من مدخلات الواجهة.

عند انتهاء الحجز يظهر تأكيد صريح ومعرّف الخطة الحالية؛ لا يقبل المتصفح وقتًا
مخصصًا أو قضية أخرى أو دورًا يدعيه. معالجة الحجز لا تعيد إرسال الجزء؛ دليل
المزود المتأخر يدخل من خدمة العامل القائمة ثم يظهر عبر زر تحديث الحالة.
الواجهة لا تتقمص العامل ولا تنشئ إيصال مزود.

## تشغيل قابل للتجربة

ثبّت المتطلبات المقيّدة في venv Python 3.13، ثم على PostgreSQL 17 أو18 محلي:

```sh
FATWA_CASE_DELIVERY_DESK_ENABLED=1 python infra/dev/with_casework_postgres.py \
  --pg-bin /path/to/postgresql/17/bin --major 17 \
  --settings apps.case_delivery_desk.settings -- \
  python -m tests.case_delivery_desk.demo --port 8018
```

المشغّل يملك قاعدة اصطناعية جديدة ويحذفها عند التوقف؛ يرفض وجود قضايا مسبقًا.
يعرض رابط الدخول ورمز الهوية الاصطناعي ومسار `demo-response.json` دون تصدير
أي مفتاح خاص. توجد ثلاث قضايا مخوّلة وقضية رابعة لا تظهر لهذا المفتي:

1. القضية الأولى: اختر حد 24 حرفًا مع التقسيم الصريح، نزّل الطلب أو عاينه، ثم
   ألصق الرد من الملف خلال أربع دقائق من التشغيل لحفظ الخطة دون إرسال.
2. الثانية: حجز فعلي اصطناعي تنتهي مهلته بعد 60 ثانية. حدّث الحالة، وافق على
   تسجيله كغير محسوم، ثم تأكد من عدم ظهور إعادة إرسال.
3. الثالثة: جميع إثباتات المزود الموقعة متحققة، مع النص الصريح أنها ليست
   إثباتًا لقراءة السائل. يمكن فتح الجواب المعتمد داخل عنصر عرض اختياري.

لإعادة تجربة الرد بعد انتهاء صلاحيته أوقف المشغّل وأعد تشغيل القاعدة المؤقتة.
الشيفرة الموقعة للبيانات الاصطناعية موجودة في fixtures الاختبار فقط؛ التطبيق
لا يستوردها. `--check` يفحص تهيئة العرض والدخول وعزل القضية الرابعة ثم يخرج.

## تحقق الرحلة

```sh
python infra/dev/with_casework_postgres.py --pg-bin /path/to/postgresql/17/bin --major 17 -- \
  python manage.py test tests.case_delivery_desk.test_http tests.casework.test_delivery \
  tests.casework.test_delivery_reconciliation --noinput --verbosity=2
FATWA_FASTBUILD_BROWSER=/usr/bin/google-chrome python infra/dev/with_casework_postgres.py \
  --pg-bin /path/to/postgresql/17/bin --major 17 -- \
  python manage.py test tests.case_delivery_desk.test_browser --noinput --verbosity=2
```

المتصفح يحتاج Playwright 1.62.0 وpyee 13.0.1 وgreenlet 3.5.5. اختبار Chrome
يمر بكامل الرحلة على 320×780 و1280×900 مع JavaScript معطل، ويكتب صورتين
وتقرير JSON في `.local/qa/case-delivery-desk/`. الصور لا تحتوي ردًا موقّعًا أو
رمز دخول/سائل أو مفتاحًا خاصًا. CI يبقي sandbox المتصفح؛ في الحاوية المحلية
فقط استُخدم `FATWA_TEST_BROWSER_NO_SANDBOX=1` لاختبار Chromium الاصطناعي.

التحقق المحلي المكتمل: 55/55 اختبارًا على PostgreSQL 17.11 وPython 3.13.5،
يشمل 11 اختبار HTTP و43 اختبار خدمة قائمًا واختبار رحلة Chromium 154 على
العرضين. كلاهما RTL بلا تجاوز أفقي أو طلب خارجي أو خطأ صفحة. نجح أيضًا
تشغيل العرض الاصطناعي بـ`--check`، وفحصا Ruff والتنسيق. يكرر CI عقود HTTP
والخدمات على PostgreSQL 17 و18، ورحلة Chrome على 17.

هذه واجهة تطوير محلية، وليست اعتماد تشغيل أو نشر. بيانات اصطناعية فقط.
