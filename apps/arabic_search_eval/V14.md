## P0 behavior and coherent authorization

`search_reference_titles` keeps the existing keyword contract and adds `page=1`,
`page_size=20` (1–20). It searches all currently permitted TOC registrations in the
requested case/edition: up to **64**, the existing source-rights case cap. This
replaces the old first-20-candidate window. Every request reloads the complete
eligible set, ranks it, revalidates it, then paginates. No global corpus search,
semantic claim, inferred rights, new index, new rights store or permission cache.

`research_workspace.reference_batch.read_locked` / `recheck_locked` are **internal
batch hooks**, not authorization entrypoints. Callers must hold canonical case
lock, staff identity, synthetic admission, `projection_expiry_guard`, and
`policy_boundary`. Public integrations should call `search_reference_titles`.
The internal hook additionally requires maintenance admission when configured.

Each phase loads registrations, latest case-specific revisions, actions and only
eligible source versions in bounded ORM batches. Denied/pending/rejected/revoked/
expired/non-READ sources never reach matching. Source paths (max five levels),
original texts, edition/archive/input pins, snapshot hashes and strict bridge
semantics are preserved using the existing resolver with freshly fetched catalog
records. Only the repeated database reads are removed. `_bridge` retains its
original live-catalog default for all other consumers.

The source ledger, exact provenance and additional workspace policy are reloaded
**after ranking**, before results, counts, facets or page hints are constructed.
Any set/revision/provenance change closes the entire response. A final whole-set
policy pass runs after later source callbacks: this rejects SEC14-01's earlier
row withdrawn during a later row's READ_METADATA check. Time expiry is checked at
the enclosing projection exit, including when the query matches zero rows.

External mutable policies must implement `ResearchRights.projection_epoch()`:

- A nonempty opaque string read atomically, without side effects.
- Covers **every** authorization input used by `permits`, including callback
  changes; never reuse an old epoch across an authorization change during a read.
- Changed policy object/epoch invalidates the entire projection at return.
- Unversioned/malformed/unavailable policies **fail closed**, rather than relying
  on an arbitrary number of scalar retries or an old cached grant.

The exact stock `SourceRightsAdapter` uses the canonical locked ledger; subclasses
and instance-overridden predicates do not take that shortcut. SyntheticRights's
added epoch is explicitly a fixture implementation over its in-memory restrictions,
not a production policy. No settings or policy for production are created.
Scalar existing search/open APIs remain otherwise unchanged. Integrator-owned
custom policies (including media-policy composites that also serve TOC searches)
must implement this contract or configure the existing stock reference adapter.

The query's original v13 word/number/normalization semantics remain unchanged.
Ranker version is now `arabic-title-words-v2-capacity64` because its bound changed.
Whole words, Arabic/Persian digit folding, retained original text and distinctions
between ة/ه, ؤ/و and ئ/ي remain. No prefix/fuzzy/semantic/embedding inference.

Output retains exact source/resource pins for existing open/cite services and adds:
`total`, `page`, `page_size`, `pages`, `next_page`, `previous_page`, and
`facets=[{printed_part,count}]`. These describe **query and location matches within
currently authorized registrations of this case/edition**, never unseen titles or
whole-book coverage. `_rights_revision` is internal and is never returned.
`coverage=CURRENT_CASE_REGISTERED_TOC`, `candidate_pool_limit=64`.

Owned research views expose signed browser-bound `research_page` actions. Opening
and returning preserve the page and filters; current rights/identity/version are
rechecked. No bearer cursor authorizes a source. Empty matches show no bogus
“page 1 of 0”. Counts/facets are derived only after the coherent batch check.

## P1 review workflow

Two new append-only models/migrations in the already-installed evaluation app:

- `EvaluationRevision`: case/number, bounded synthetic corpus, proposed judgements,
  separate canonical SHA-256 digests, ranker version **plus ranking.py SHA-256**,
  author/provider/auth epoch, reason and timestamp.
- `EvaluationDecision`: one independent APPROVE/REJECT decision, every query's
  explicit AGREE/DISAGREE and explanation, reviewer identity and timestamp.

Every version begins PENDING. Changes create a numbered successor and preserve
old corpus, judgements, decisions and timestamps. A fresh corpus/expectation
revision never inherits approval. Decisions require exact current version/hashes/
ranker identity, explicit confirmation, complete unique query judgements, and a
reviewer distinct from the author. APPROVE requires all AGREE; REJECT preserves
all entered judgements. DB triggers reject update/delete, self-review, stale
version decisions and invalid sequence/bindings. Changes to policy/identity after
insertion roll the transaction back.

Public services: `review.propose`, `review.decide`, `review.history`, all under
existing canonical case scope and maintenance admission. **Default disabled**:
`FATWA_ARABIC_SEARCH_REVIEW_ENABLED=True` plus an explicit server-configured
`FATWA_ARABIC_SEARCH_REVIEW_AUTHORITY` implementing `EvaluationAuthority` are
required. Actions VIEW/PROPOSE/APPROVE/REJECT have no implicit role grant.

The private RTL form uses the existing `/casework/staff/` native POST/CSRF/budget
boundary; no extra route, guard exception, shared template or settings change.
Research `ACTIONS` now includes:
`research_evaluation_open`, `research_evaluation_propose`,
`research_evaluation_APPROVE`, `research_evaluation_REJECT`, and `research_page`.
Coordinator dispatchers should continue routing this owned ACTIONS set to
`research_workspace.views.workspace`. The reviewer chooses a verdict and reason
per query in ordinary forms; dataset authoring is a bounded JSON form with the
current proposal prefilled. This is not a grant to upload private source texts.

**No actual human reviewed the committed fixture.** Test approvals use explicitly
synthetic identities in destroyed test databases. A stored decision applies only
to its exact corpus/judgement/ranker identity. It never approves a fatwa, source
right, deployment, or the global ranker. The committed v13 benchmark remains
AUTHOR_PROPOSED_REVIEW_PENDING. Search does not automatically label itself human
approved after a synthetic workflow test. D-023 / original requirements 243–244
remain pending specialist-reviewed gold data; no acceptance upgrade is claimed.

## Measurements and validation

Fresh baseline test on #232: **558 SQL, 0.4705 s**, four authorized candidates,
one result. Same fixture after batch repair on PG17: **24 SQL, 0.0250 s**; PG18:
**24 SQL, 0.0443 s**. A 24-candidate fixture also uses **24 SQL** (one-candidate
comparison: 24); final result pages reach rows beyond the former 20 boundary.
The initial 24-source run was 168 queries because the bridge still performed
per-row DB lookups; that regression was fixed and its growth assertion retained.

These are individual local samples, not an SLO or load benchmark. The PG17 and
PG18 runs initially overlapped; latency is noisy and not comparable across hosts
or patch builds. SQL count, exact identity/rights and relevance assertions are the
regression gates. An external custom policy can add its own DB/network cost; the
constant-query claim covers the batch implementation with the explicit synthetic
policy, not arbitrary policy backends.

`metrics_v14.json` binds the unchanged 28-title / 42-query fixture and current
ranker/service code. Compared with **V13's improved ranker**, relevance is
unchanged: precision@5/recall@5/MRR@5 = 1.0 on the same authored positives,
36/36 valid proposed orders, 0/7 negative false-positive queries, six invalid
queries rejected. This deliberately small non-held-out synthetic dataset is not
human gold or proof of corpus-wide recall. The older substring baseline numbers
remain historical; they are not a new V14 relevance improvement.

Evidence in `evidence/v14/`:

- PG17.11: 25/25 focused tests passed; PG18.7: 25/25 passed. These include the
  unmodified external SEC14-01 reproducer.
- After the additional internal maintenance-admission assertion, the affected
  adapter/batch/security boundary suite passed **14/14** separately on both majors.
  There are 26 distinct non-browser tests across these overlapping focused runs.
- A Chrome UI journey passes with keyboard activation, independent synthetic
  contexts, page/open/back, PENDING→decision and 320/1280px no horizontal overflow.
  External requests are blocked. Screenshots are in `evidence/browser/`.
- **Browser boundary limitation:** native sandbox launch failed because the
  environment's SUID helper is owned by nobody, not root. The UI-only run used
  `FATWA_BROWSER_SANDBOX=0` inside the existing isolated synthetic executor. It is
  not sandbox/security clearance; the integrator must rerun the committed test
  with its default sandbox enabled in a correctly configured environment.
- Source/SQL locks, callback mutation, expiry and transaction rollback are distinct
  claims. Tests cover actual same-connection ledger changes (rolled back with a
  denied response) and a separately committed subsequent revocation. They do not
  claim simultaneous cross-connection SQL revocation timing.
- Development failures retained: nested main markup and a malformed select option
  were caught and corrected by Chrome; unknown standalone review route was moved
  into the existing guarded staff POST; domain denial was corrected from 400 to
